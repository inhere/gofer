# 三期计划：Team（leader + 成员 + 信箱路由 + 团队页）

> issue：gofer-0py5（三期）；吸收 gofer-ayas（Squad 重做），为 gofer-9dbh（工作区代理）铺路
> 设计：`docs/design/2026-11-18-resident-sessions-and-team-design.md` §7（方向已批，Q4 按推荐：leader + 成员 + 信箱 + 确定性路由，不做自由群聊）
> 状态：**已批**（2026-11-26，§4 六项按推荐；跨项目协作走两个 leader 互发信件）

## 0. 计划级决定

1. **团队由 seat 组成，不由会话组成**。一个团队有一个 leader seat 和若干成员 seat，都在同一项目。seat 换了会话，团队关系不变。名册、流程步骤、「等我」这些都从 seat 现有的数据取。
2. **路由是确定性的，在服务端判定**。路由不由模型决定谁发言，每次判定都落库，可以查询。leader 只派活和汇总，不写实现，也不能把流程推到 done（done 和批准仍然只能由人来做）。
3. **建在信箱上，不另建一条消息通道**。团队里的信件就是普通信件，多带团队、跳数和路由键几个字段；送达、离线排队、退信、暂停都沿用信箱现有的做法。
4. **拆两步**。3a 是实体、地址、路由、leader 协议注入、评估记录和 CLI。3b 是 web 团队页、「等我」团队卡和真机验收。3a 发版后先在本工作区跑一个小团队，再做 3b。
5. **默认不建任何团队**。不配置就没有任何行为变化。

## 1. 现状要点（代码摸底 2026-11-26）

- **信箱**
  - 地址有 7 种：session / job / topic / path / caller / agent / project（project 只能写 `each:project:`）。没有 `seat:` 地址，按 seat 寻址时，seat 换了会话旧地址就失效。
  - 投递：服务端路径（suga、ACP say、agent 常驻）至少一次，claim 带租约，再 send，再 confirm，标签里带信件 id。hook 路径至多一次。两条路径都没有幂等键，也没有去重。
  - 合并：终端会话的多封信只发一次 wake，下一回合一次注入；ACP job 每轮扫描只 say 一封，不合并。
  - 信件字段有 thread_id、reply_to、from_*、urgent、attempts、broadcast_id。没有跳数字段，只有每个对话串最多 20 封的上限。回信默认回给原发件人。
  - 已有的开关：暂停送达、群发（`each:`，上限 20 人）、急件、发信限速。
- **seat**
  - 名册字段有 state（none / running / awaiting / offline / ended / failed）、waiting、activity_at、current_ref；2c 的 C1 合入后还会有 stage。
  - seat 没有分组字段。
  - 章程只在终端 SessionStart、ACP bind 或 restart 时注入，不是每回合注入。
- **每回合注入**
  - 终端：UserPromptSubmit 的拼接顺序是 catchUp → 记忆 → stage 行。
  - ACP：TurnNote 由 needsReply、目录锁和 stage 行拼成。本机与远端 worker 是两条拼接路径，都有 StageNoter 这个接缝可以照着做。
- **「等我」**：照 stage_cards 新写一个数据源，挂进 WaitingSubjects 和 signalsOf，补上 kind 映射即可，kind 覆盖测试会强制检查。
- **web**：有通用时间线组件 `ConversationTimeline.vue`，以及 `SeatRoster*` 名册组件和 `/mail` 对话页可以复用。

## 2. 方案

### 2.1 实体

- `teams`：id、project_key、name（项目内唯一）、leader_seat_id、brief（团队说明，只注入给 leader）、relay_mode（leader / direct，默认 leader，3a 只实现 leader）、relay_round_limit（默认 3）、relay_daily_limit（默认 20）、merge_window_sec（默认 120）、archived_at、created_at、updated_at。
- `team_members`：team_id、seat_id、role（member）、added_at。一个 seat 同一时间最多属于一个团队。leader seat 不能同时是成员。
- `team_routes`：每次路由判定一行，字段有 team_id、mail_id、from_ref、to_seat_ids、rule、hop、route_key、decided_at、outcome（pending / delivered / queued / merged / handed_to_leader / dropped_self / dup / held / unknown）。
- `team_evals`：leader 每轮的评估，字段有 team_id、leader_ref、turn_ref、outcome（dispatched / idle / failed）、reason、at。

### 2.2 地址

- 新增 `seat:<name>[@<project>]`，解析为该 seat 当前坐着的会话。seat 空着时信件 held 并进收集箱；seat 离线时照常排队，回来后送达。
- 新增 `team:<name>[@<project>]`，等价于发给 leader seat，并标上团队。
- 这两种地址也能在团队之外单独用，信箱 CLI、HTTP、MCP 都支持。

### 2.3 路由规则（确定性，按顺序判定，都落 `team_routes`）

1. **leader 自己发的信不唤醒自己**（规则 `self`）：leader 写给团队或写给自己的信只记录，不投递。
2. **人发给团队**：正文点了名（`@成员名`）的信只送给被点名的成员；没点名的信只送给 leader（规则 `human_named` / `human_default`）。
3. **成员发出的结果信**：没有显式收件人，或者收件人写的是 `team:`，都送给 leader（规则 `member_result`）。
4. **agent 点名 agent**（规则 `relay`）：允许点名，转发时 hop 加 1（hop 只用于标注）。回环防护按路由账本计数，不按单链深度：同一对成员之间头部连续来回超过 3 轮，或同一团队 24 小时内成员间转发超过 20 次（两个数是团队配置，默认 3 / 20），这封信改送 leader，并记为 `handed_to_leader`，不丢弃。leader 派活、第三方加入、转给人都会断开连续计数。
5. **幂等**：转发信带 `route_key`（源信件 id + 目标 seat），同一个 key 只投一次。重复的信记为 `dup`，不投递。账本先写一条 pending 记录再投递，投递结果出来后结清（delivered / queued / merged / …）；结果拿不到时记 `unknown`，保持未结、按 route_key 对账，不盲目重投。回环计数只数结清为已投递的。job 里发信由 CLI 按 job id + 收件人 + 正文哈希自动带幂等键，超时重跑同一条命令不会重复发。
6. **合并**：目标会话已经有待跑的一轮时，新信并进那一轮。ACP 收件在取信（claim）时把排在队头、merge_window_sec 内的多封信合成一次 say，正文按封分段并标出来源，被并入的信记 `merged`，后续回信归到合并它的那一轮。遇到人的信、急件或另一团队的信就停止合并。终端本来就是一回合一次注入，不用改。
7. 来源标注：每封转发信正文前加一行 `[team <name> · from <seat> · hop n]`。
8. **身份以服务端为准**：leader 才有的动作（team eval、派活标注）只认 leader seat 上的 job / 会话凭据，不认信件里自称的身份；证明不了就按普通成员处理。
9. **成员 job 失败**：成员 seat 上的 job 失败时，服务端给 leader 发一封系统信（规则 `member_failed`），不发给交接它的成员，避免失败恢复形成回环。leader 不可达（seat 空着或已结束）时依次改送团队创建者、再到人的「等我」。
   - **系统信是终点**：`member_failed`、`handed_to_leader` 摘要、超限通知这类系统信不再触发路由，不计入回环计数，也不会再次升级。
10. **外项目 leader 来信**（规则 `peer_leader`）：另一项目的团队 leader 发来的信只送给本团队 leader，正文里的 `@成员名` 不生效；回信默认回给对方 leader。跨项目往返同样计 hop，回环防护按第 4 条（两个 leader 算一对）。

### 2.4 leader 协议

- **每次唤醒都注入**（终端 UserPromptSubmit 和 ACP TurnNote 两端都加）：协议正文 + 花名册 + 团队说明。花名册每行写成员名、用途、状态、当前流程步骤、最近活动时间。照 StageNoter 新加一个 `TeamNoter` 接缝，本机与远端 worker 两条路径都接上。
- **评估**：leader 每轮必须执行 `gofer team eval --outcome dispatched|idle|failed --reason "…"`。一轮结束时还没有评估的，记一条 `missing_eval`。连续 3 轮缺评估，生成一张「等我」卡。没有事情的那一轮不发信，只记评估。
- **评估绑定到这一轮**：`team eval --outcome idle` 之后，同一轮里 leader 再往团队发信，服务端拒绝（409）。
- **链条结束通知人**：leader 被成员结果唤醒，这一轮既没发信、也没派活、也没留唤醒时，视为这条链结束，把触发它的那封结果信作为团队结果推给人（「等我」卡 / 通知）。
- **花名册与就绪通知只是信息**：它们走注入，不进信箱队列，不可认领，不触发超时催办，也不算作 leader 这一轮「有事」。
- **注入里的信件正文是不可信输入**：协议与花名册放固定段，信件内容放每轮可变段，用每轮随机的边界标签包住，防止正文伪造协议段。
- **约束**：在 leader 会话里执行 `stage done` 时，如果下一步是 done，服务端拒绝（只有人能完成工作项）。leader 可以自己做 design 和 plan 步的文档，但协议里写明「实现交给成员」。这一条靠协议约束，不做硬性限制。

### 2.5 CLI（`gofer team`，核心资源名词，顶级组）

`team add <name> --leader <seat> [--brief @file]`、`team member add|rm <team> <seat>`、`team ls|show`（show 显示花名册与最近的路由）、`team say <team> "<text>"`（人发给团队，按 2.3 第 2 条路由）、`team routes <team>`（判定记录）、`team eval`（leader 用）、`team rm`（归档）。

### 2.6 web（3b）

- **团队页 `/team?id=`**：左边是成员列表（状态点、当前步骤、未读），右边是公开层时间线（成员之间的信件、流程事件、「等我」卡、leader 评估），用 `ConversationTimeline` 渲染。点一条结果，跳到产出它的成员会话所在的工作台线程。
- 时间线底部有一个输入框，就是 `team say`。
- 「等我」新增团队卡：leader 连续缺评估、转发超限改送 leader、团队成员全部离线但还有待送信件。

### 2.7 参考吸收（2026-11-26）

multica（Squad 更新）与 lobehub（Channel 子系统）的近期做法已并入上面：回环按账本计数、超限转 leader（2.3 第 4 条）；账本投递后才写、job 内发信自动幂等（第 5 条）；取信时合并并记 `merged`（第 6 条）；leader 身份以服务端为准（第 8 条）；成员失败送 leader（第 9 条）；评估绑定到这一轮、链条结束通知人、注入随机边界（2.4）。预留团队字段 `relay_mode`（leader / direct，3a 只实现 leader）。OpenRig 的近期做法并入：投递先记 pending 再结清、`unknown` 对账（第 5 条）；系统信是终点、leader 不可达时逐级改送（第 9 条）；花名册只作信息（2.4）。明细见 `docs/refer/reference-projects.md`。

## 4. 决策点（2026-11-26 已批：全部按推荐）

- **Q1 团队范围**：只做项目内团队，leader 和成员都在同一项目。需要跨项目协作时，由两个团队的 leader 互相发信（`team:<name>@<project>` 或 `seat:<leader>@<project>`），不做跨项目团队。T1 的地址解析与 T2 的路由要覆盖这条路径：外项目 leader 发来的信按「人发给团队」以外的来信处理，只送给本团队 leader（规则 `peer_leader`），不直接点名本团队成员。
- **Q2 人是否作为成员**：推荐一期不做。人始终是团队的主人，通过「等我」卡和团队页参与，用 `team say` 发言。设计 §7 里「人也可以是成员」留到后面。
- **Q3 leader 用什么 seat**：推荐任意 seat 都可以（终端或 ACP）。长期无人值守的团队，建议用 ACP seat 当 leader，这样能被信件唤醒。
- **Q4 唤醒成本**：成员每发一封结果信都会唤醒 leader。推荐给 leader 设合并窗口，默认 120 秒，窗口内的信合成一轮；也可以按团队把它调成 0。
- **Q5 工作区代理（gofer-9dbh）**：推荐三期不做。三期做完后，工作区代理就是「一个工作区级团队的 leader」，到时再定。
- **Q6 命令名**：推荐 `gofer team`，作为顶级资源名词，按 G033 需要你确认。
