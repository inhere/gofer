# gofer 文本国际化（agent 提示词 / CLI / 服务端文本）设计

> issue：gofer-992q
> 状态：0.2 已批准（2026-10-27，三个待确认项按推荐）
> 相关：gookit/i18n v1.3.0（新增 `fs.FS` / `embed.FS` 加载）；G046（对外产物按通用平台视角写、一个 prompt 内不中英混杂）；G045（用户可见变化同步 skill references）

## 1. 背景与问题

Web 控制台已经有完整的 zh / en（P6）。服务端与 CLI 仍大量写死中文：`internal/` 下 224 个 Go 文件含中文字符串字面量。英文界面下派任务时，gofer 注入给 agent 的「验收标准 / 汇报格式 / 交付约定」等段落仍是中文，英文用户的 agent 收到中英混杂的提示词。

按受众分三类（统计为含中文字面量的非测试文件数 / 约行数）：

| 类 | 内容 | 主要位置 |
|---|---|---|
| ① 注入给 agent 的文本 | 任务说明段落、worktree 交付说明、续接 / 自动续投提示、hook 注入（记忆、信件、提问）、管家提示词、系统消息前缀、MCP 工具说明与返回给 agent 的错误、brief / prime 输出 | job（34 / ~480）、hookrelay（10 / ~135）、steward（6 / ~196）、sessionrelay（11 / ~153）、mail（8 / ~96）、msgprefix（1 / ~42）、mcpserver（9 / ~79）、brief（8 / ~193） |
| ② CLI 输出与错误 | 命令说明、提示、表格表头、错误信息 | commands（23 / ~424） |
| ③ 服务端生成、在 web 上显示的文本 | 今天页卡片摘要、工作项日志、事件说明、通知正文、HTTP 错误 detail | today（7 / ~228）、work（14 / ~381）、notify、httpapi（31 / ~447） |

## 2. 目标与非目标

目标
- 阶段 1：① 全部按语言输出，英文用户的 agent 拿到的提示词里没有中文；英文推广（HN / Reddit）以此为前置条件。
- 阶段 2：② CLI 按调用方语言输出。
- 阶段 3：③ 服务端文本按查看者 / 配置语言输出。
- 每个阶段完成后，迁移过的包不再新增写死的中文（扫描测试守住）。

非目标
- 不支持 zh / en 以外的语言（结构上允许以后加，但不承诺）。
- 不翻译用户自己写的内容（任务 prompt、issue、记忆、信件正文）。
- 不改 Web 已有的 i18n 结构。
- 代码注释不在范围内（扫描测试排除注释）。

## 3. 语言从哪来

| 文本 | 语言来源（从高到低） |
|---|---|
| 注入给某个 job / 会话的文本 | 该 job 的项目 `projects.<p>.language` → `server.language` |
| 发给会话的系统消息（`[gofer · …]` 一类） | 收件会话所属项目的语言 → `server.language` |
| CLI 输出 | `GOFER_LANG` 环境变量 → 客户端配置 `language` → 系统语言（`LANG` / `LC_ALL`；Windows 取用户界面语言） → `en` |
| 服务端生成、在 web 显示的文本（阶段 3） | 请求头 `Accept-Language`（web 已有语言设置，随请求发送） → `server.language` |

配置值规范为 `en` | `zh-CN`。**所有入口统一经 `i18n.Normalize`**（唯一入口，类似 G043 的 runner 名归一化）：配置加载与写入（`server.language`、`projects.<p>.language`、客户端 `language`）、`GOFER_LANG`、系统语言（`LANG` / `LC_ALL` / Windows 界面语言）、HTTP `Accept-Language`、CLI `--lang`（若有）。保存（写配置、写 job 请求）一律存规范值；读到别名也按规范值使用。

| 规范值 | 接受的别名（大小写不敏感，`-` / `_` 等价，忽略编码与修饰如 `.UTF-8`、`@euro`） |
|---|---|
| `en` | `en`、`en-US`、`en-GB`、`en_US.UTF-8`、`english`、`eng`、`C`、`POSIX`（系统语言为 C / POSIX 时按英文） |
| `zh-CN` | `zh`、`zh-CN`、`zh_CN.UTF-8`、`zh-Hans`、`zh-Hans-CN`、`zh-SG`、`cn`、`chinese`、`中文`、`简体中文` |

`zh-TW` / `zh-HK` / `zh-Hant` 暂按 `zh-CN` 处理（只有简体文案），在实施记录里注明。无法识别的值：配置校验报错并列出可用值；环境变量 / 系统语言 / `Accept-Language` 识别不了时回退到下一级来源。`Accept-Language` 按 q 值顺序取第一个能识别的。

**兼容与默认**
- `gofer init` 生成的新配置按系统语言写入 `server.language`。
- 配置里没写 `server.language` 时：取 `zh-CN`，即现有部署升级后行为不变；同时在启动日志与 `config validate` 里提示「请显式设置 server.language」。代码里标 `// DEPRECATED(v0.19x): default flips to en in v0.2xx`，按 G032 三个版本后把缺省改成 `en`。
- 已定：缺省先用 `zh-CN`，三个版本后改为 `en`（见第 9 节）。

## 4. 文本放在哪里、怎么取

新增包 `internal/i18n`（入口层与业务层都可用；只依赖标准库与 gookit/i18n）。

**短文本**（一行或一句：CLI 提示、错误、表头、通知标题、事件说明）
- 用 gookit/i18n v1.3.0，`DirMode` + `embed.FS`：`internal/i18n/lang/{en,zh-CN}/<domain>.ini`，按领域分文件（`job.ini`、`mail.ini`、`cli.ini` …）。
- 键名：`<领域>.<区域>.<名字>`，例如 `job.review.waiting`、`mail.bounce.subject`；与 web 的键名规范一致。
- 参数用命名替换（gookit/i18n 的 `ReplaceMode`，`{name}` 形式），不用位置参数，便于两种语言调整语序。
- API：`i18n.T(lang, key, args...)`；`i18n.Lang` 类型 + `i18n.Resolve(...)` 按第 3 节的来源决定语言。

**长文本**（注入给 agent 的多行 markdown：验收段落、汇报格式、交付约定、worktree 说明、管家角色提示、续接提示）
- 不放 INI。每种语言一份 `text/template`：`internal/i18n/prompts/{en,zh-CN}/<name>.md.tmpl`，同样用 `embed.FS` 加载。
- 模板只做变量替换与少量条件，不写业务逻辑；变量由调用方传入结构体，字段名两种语言共用。
- API：`prompts.Render(lang, name, data) (string, error)`；启动时预解析全部模板，缺模板或解析失败直接报错（不在运行时才发现）。

## 5. 协议文本：不能简单翻译的部分

这些字符串会被程序解析或识别，换语言要保证新旧都能认：

| 协议文本 | 谁在解析 | 方案 |
|---|---|---|
| 汇报小节「## 发现但不碰」「## 可复用经验」 | `internal/job/findings.go`、`knowledge.go`、CLI `job findings`、记忆候选 | 提示词里按语言写（英文为 `## Out-of-scope findings`、`## Reusable lessons`）；解析器同时接受两种语言的小节名（别名表放 `internal/i18n`，一处维护） |
| 系统消息前缀 `[gofer · job 完成]` 等 | 会话侧 hook、web 区分人 / 系统消息 | 生成时按语言（英文如 `[gofer · job done]`）；识别统一按开头 `[gofer · ` 判断类型，并接受两种语言的类型名 |
| 用户消息前缀 `[来自 web，<用户>]` / `[来自 web 回复，…]` | hook、web | 同上：生成按语言（`[from web, <user>]` / `[web reply, <user>]`），识别两种都认 |
| 管家提示词开头 `# 你是工作管家` | `web/src/utils/steward.ts` 识别首轮 prime | web 端改为识别两种语言的开头，或改用语言无关的标记（例如提示词首行加 `<!-- gofer:steward-prime -->`）；倾向后者 |
| 信件注入的 `<gofer-mail …>` 标签 | hook 与 agent | 已是语言无关结构，标签不翻译，只翻译其中的说明文字 |
| CLI / HTTP 的机器可读输出（`--json`、错误 `error` 字段的固定短语） | 脚本、MCP 客户端 | 不翻译；只翻译给人看的 `detail` |

别名与识别逻辑集中在 `internal/i18n/protocol.go`，各解析器调用它，避免各写一份。

## 6. 分阶段

**阶段 1（英文推广前必须完成）**：类 ①
1. 建 `internal/i18n`（短文本 + 模板 + 语言解析 + 协议别名），配置项 `server.language` / `projects.<p>.language`，`gofer init` 写入，`config validate` 提示。
2. 迁移顺序：job 提示词段落（`prompt_sections.go`、`branch_delivery.go`、`model.go` 中的说明）→ 续接 / 自动续投提示 → hook 注入（记忆、信件、提问）→ msgprefix → sessionrelay 发给会话的文本 → mail 渲染与退信 → 管家提示词 → mcpserver 工具说明与返回给 agent 的错误 → brief / prime。
3. 协议文本按第 5 节同时兼容新旧。
4. 测试：两种语言各渲染一遍全部模板（golden 文件）；解析器对两种语言的小节名与前缀都有用例；扫描测试守住已迁移的包。
5. 文档：skill references（job / sessions-relay / mail / steward）与配置示例同步；英文文档说明 `server.language`。

**阶段 2**：类 ② CLI。按命令组迁移，`--help` 说明文字也在内；`GOFER_LANG` 与客户端配置。

**阶段 3**：类 ③ 服务端显示文本。HTTP 读取 `Accept-Language`；今天页卡片、工作项日志、事件说明、通知正文、HTTP 错误 `detail`。已经存进数据库的历史文本不回写，只影响新生成的。

每个阶段按包拆成若干 job，可以并行；每个包迁移完成就把它加进扫描测试的「已迁移」清单。

## 7. 测试与守护

- **键与模板对齐**：zh-CN 与 en 的 INI 键集合完全一致；两种语言的模板文件名一致，且模板里引用的变量集合一致。
- **golden**：阶段 1 的每个模板，在两种语言下用固定数据渲染，结果写 golden 文件；改文案时更新 golden，评审时能直接看到变化。
- **扫描测试**：已迁移包里的 Go 字符串字面量不得含 CJK（排除注释、测试、`internal/i18n` 自身、协议别名表）；新写死的中文直接失败。
- **协议兼容**：每个识别点对旧中文形式与新英文形式各一例。
- **端到端**：`server.language: en` 下派一个 `--review --worktree` 任务，渲染出的完整提示词里没有 CJK（测试里用 exec agent 回显 prompt 即可）。

## 8. 风险

- **提示词措辞变了，agent 行为可能随之变化**：英文版不是逐字翻译，按英文写法重写，但要求、顺序和小节名保持对应。中文版本身不动，现有部署（`zh-CN`）的行为不变。
- **范围大**：阶段 1 约 90 个文件。按第 6 节的顺序拆小，每一步都能单独合并发版。
- **协议兼容遗漏**：第 5 节的表格是清单；实施时 `git grep` 所有识别点（`strings.HasPrefix`、正则）再核一遍，补进表格。

## 9. 已定事项（2026-10-27）

1. `server.language` 缺省先用 `zh-CN`：现有部署升级后行为不变；启动日志与 `config validate` 提示显式设置；代码标 `DEPRECATED`，三个版本后缺省改为 `en`。
2. 管家首轮提示词的识别改用语言无关的标记：提示词首行 `<!-- gofer:steward-prime -->`，web 与服务端都按标记识别；旧的中文开头在过渡期仍然认。
3. 英文系统消息前缀：`[gofer · job done]`、`[gofer · wakeup]`、`[gofer · work handoff]`、`[gofer · work report]`、`[gofer · steward relay]`、`[gofer · memory]`、`[gofer · hint]`、`[gofer · bounce]`；用户消息前缀 `[from web, <user>]`、`[web reply, <user>]`。识别两种语言都认。

- **语言来源** `lang.go`：`backendLang(b Backend)` —— Backend 实现 `Language()` 时用它（`localBackend` 直接读 `jobs.Config().Language()`，即 `server.language`），否则回落 `i18n.FromEnv()`（GOFER_LANG → 系统语言 → 缺省），这是瘦客户端转发到中央 serve 的情形：中央的 `server.language` 到不了这个进程（`GET /v1/meta` 没有 language 字段）。**通道不对等，需要后续定**：要么 `/v1/meta` 加可选字段，要么把 job 的语言经 env 传给 agent 进程（`GOFER_LANG`），本项未自行扩协议。工具说明在构建 server 时固定，换语言需新开 MCP 会话（agent 每次本来就会开）。
- **文本分层**：完全用英文写的说明留在 Go 里（两种语言同一份）。带语言措辞的 14 处（`「今天」`、`「按建议：X」`、`「采纳」`、`「忽略」`、`「## 可复用经验」`、`「⚠ 待复核（reason）」`、`(高危/拿不准, 留给人处理)`、`带话`、`@<agent 或 role>`、`改动分组 / 风险 / 测试`、两份 `gofer_*_brief` 说明、两条错误）走新目录 `internal/i18n/lang/{en,zh-CN}/mcp.ini`（`[mcp.term]` / `[mcp.desc]` / `[mcp.error]`）。拆开会把任一语言读断的整句放 `mcp.desc`，其余用 `mcp.term` 拼接。
  - 已验过 INI 值能原样保留 `##`、引号、全角括号、em dash、`` ` ``、`%q`、`{占位}`，所以长说明直接放值里，未另立模板。
  - 带参数的只有 `mcp.error.project_scope_denied`（`{scope}` / `{project}`，project 传 `strconv.Quote`，所以引号与迁移前一致）。
- **测试** `lang_test.go`：`testdata/descriptions-zh-CN.golden` 是**迁移前代码**跑 `tools/list` 的导出（66 个工具，逐行 name\tdescription），`TestZhDescriptionsUnchanged` 逐条比对；英文 66 条无 CJK；`TestMcpTextFollowsLanguage` 用字面量钉住两种语言的 12 条目录文本；`TestProjectScopeRefusalIsLocalized` 走 scoped server 实际拒绝一次，钉住中 / 英两句；`TestMcpFilesHaveNoCJK` 扫描本包非测试文件的字符串字面量。
