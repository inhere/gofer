## 1. 问题（用户 2026-11-18 原话归纳）

1. **长期会话多、难找难续**：每个工作区固定 2–3 个终端会话，各自主跟进一个或几个相关项目，长期使用、基本不 clear；另有固定用途会话（审查清理代码仓库 PR、分析工作区近一周工作、按固定格式写周报、部署工厂 / 内网服务），关了下次还要找回来继续，找起来要切到对应工作目录。合计 10+ 个。
2. **开工前要手动提醒建 plan**。
3. **中大功能都走 idevstd 的 design → review → plan → doing，会话常忘，要人提醒**。
4. **跟进不过来**：切过去才发现在等确认。要按流程自动推进（类似 SOP），并把这些终端会话迁到 gofer web：能看到哪些需要我、主动弹窗找我。
5. 想在 gofer 已有能力上做类似 Team / 群组的功能。

## 2. 现状与缺口

| 需要 | gofer 已有 | 缺口 |
|---|---|---|
| 会话找回 | 会话页（终端会话列表、回复 / 接管 / 唤醒 / 催办）、工作台（ACP 线程、置顶、`?thread=` 深链）、托管常驻会话 `--hosted`、`session resume` | 会话没有**稳定身份**：一次 Claude Code 进程 = 一行会话，换进程、隔天再开就是新行；没有「这个会话是干什么的」；找回要人记目录和会话 id |
| 固定用途 | 定时任务（schedule）、job 模板、记忆 | 定时任务每次新开 job，不能「始终在同一会话里继续」；固定格式 / 审查清单靠人每次贴 |
| 流程 | plan / todo、plan 推进引擎（只记录）、`--review` 验收、workflow 引擎、SessionStart 注入（repo prime） | plan 之前的 design / review 阶段 gofer 不知道；没有「你在哪一步、下一步是什么」的每轮提醒；没有服务端判定的阶段门禁 |
| 需要我 | 「等我」（RV2 误报 4%）、桌面通知、Web Push、`[needs-reply]` 标记 | 推送与「等我」不同源（RV2：97 条推送 60 条多余）；web 内没有一次一件的弹卡；页面失焦时不弹浏览器通知；工作台已有「需要你 / 活跃 / 空闲」分组与置顶，但只含 ACP 线程，终端会话不在里面，且前端把每个停在 awaiting_input 的 ACP 线程都算「需要你」，与服务端口径不一；托管 ACP 会话等回复只有一次性推送，不进「等我」 |
| Team | 会话信箱（mail）、会话间提问、子 job 回执唤醒 | 没有团队实体、成员路由规则、leader 协议；Squad 旧实现已退役 |

## 3. 方案总览

四块，按依赖分三期：

- **A 常驻会话名册**（一期）：给长期会话一个稳定身份，跨进程、跨天都是「同一个」。
- **C 主动找人**（一期，与 A 同批）：「等我」单一来源，web 弹卡、浏览器通知、会话分桶都从它派生。
- **B 流程推进**（二期）：design → review → plan → doing 由服务端维护状态和门禁，每轮提醒，按放权等级推进。
- **D Team**（三期）：在 A + B 之上，一个 leader 常驻会话 + 成员常驻会话，靠信箱和确定性路由协作。

各期分别出计划、分别评审；本稿只定方向、边界与决策点。

## 4. A 常驻会话名册

### 4.1 实体

`seat`（常驻会话，CLI `gofer seat`；不叫 `resident`，因为代码里 resident 已指 ACP 持续会话 job（`job resume --mode session`、`MailResidentAgent` 等），同名会混淆）：

| 字段 | 说明 |
|---|---|
| `name` | 同一用户、同一工作区内唯一的短名（跨工作区用 `name@project`）（如 `gofer-dev`、`pr-review`、`weekly-report`），CLI 与 web 都按它找 |
| `project` / `cwd` | 所属工作区与工作目录（找回时不用人记目录） |
| `purpose` | 一句话用途，显示在列表上 |
| `charter` | 规范文档路径或正文（固定格式周报模板、PR 审查清单、本会话主跟进的项目与约定）；会话开始与 compact 之后注入；由会话里的 agent 修改时要标出并留历史（它会注入之后每个会话，是一条持久注入通道） |
| `kind` | `terminal`（终端里的 Claude Code / codex 等，经 hook 登记）或 `acp`（gofer 托管的 ACP 会话） |
| `current` | 当前绑定的会话（终端会话 id 或 ACP job id）；历史绑定保留，可回看 |
| `flow` | 默认流程模板（二期用，见 §6） |
| `schedule` | 可选：定时在**同一会话**里发一轮固定话术（周报、周分析） |
| `pinned` / `order` | 侧栏固定顺序 |

### 4.2 绑定与续接

- **绑定**：以人为主——web 会话行「设为常驻」，或人在终端执行 `gofer seat bind <name>`；之后同一 agent 会话 id（Claude Code `--resume` / `--continue` 后 id 不变）自动续绑。换了新会话 id（含 `/clear`）不自动换绑：web 会话行和「等我」里显示「是否设为 X」，由人确认。不把绑定命令写进给 agent 的注入（同目录 2–3 个会话时会被诱导抢绑）；只是离线的 seat 不算空位。seat 不承载会话授权。
- **找回**：`gofer seat open <name>` 打印（或直接执行）进入目录并续接的命令（如 `cd <cwd> && claude --resume <id>`）；web 名册行上「在终端继续」一键复制同一条命令；`acp` 类直接打开工作台线程。
- **续接告知**：续接不上（会话文件不在、agent 不支持）时新开，并注入 charter + 上次的进展摘要（取最近的 `work report` / plan handoff），明确告诉 agent「这是新会话」，不假装记得（参照 Multica 续接提示）。
- **固定会话定时**：`schedule` 到点时向 `current` 会话送一轮固定话术（复用现有定时任务 schedules，投递目标为 seat；不用会话催办 nudge，会话结束它就永久关闭）；会话不在线时，`acp` 类拉起托管会话，`terminal` 类进「等我」提示人去打开（不替人起终端）。

### 4.3 迁到 web

两条路并存（Q1）：

- **终端会话留在终端**：web 名册显示状态、等我、最近回合，经现有送话回复；适合习惯终端操作、需要本机 TTY 的会话。
- **托管 ACP 会话**：会话本体由 gofer 托管（`--hosted`），web 原生对话；适合固定用途会话（周报、PR 审查、周分析），不占终端窗口。从终端迁入：若 Claude 的 ACP 适配器能 `session/load` 终端 Claude Code 写下的会话（**待核实**），可原地接续；不能就按 §4.2「续接告知」新开。

### 4.4 界面

- **名册侧栏**（工作台左侧，参照 LoopForge / LobeHub；在现有工作台分组、置顶与布局上扩展，不另起一套）：按工作区固定顺序分组，组内置顶在前；**打开或回复不改变顺序**；每行：名字、用途、状态点（回复中 / 等我 / 失败 / 空闲）、未读点。顶部一个「需要我」桶汇总所有组里等我的会话。
- **底部会话标签栏**（参照 Multica；一期不做，放到一期之后视需要）：常驻会话各一个标签，转圈 = 回复中、彩点 = 等我或未读；关掉的标签有新消息自动回来；`Mod+K` 按名字跳转。
- 非常驻的临时会话仍在现有会话页 / 工作台，不进名册。

## 5. C 主动找人

- **单一来源**：「等我」是唯一判定；推送、web 弹卡、浏览器通知、名册状态点全部从它派生（gofer-hzz3：推送改同口径，宽限期满再发、发前复核仍在等）。
- **web 弹卡**（参照 LobeHub）：当前不在屏的会话进「等我」时，顶部中间弹一张卡，一次一件（其余显示 +N），可就地作答 / 批准或跳转；关掉只隐藏，「等我」里保留；关闭状态存服务端，多个浏览器同步。
- **浏览器通知**：页面失焦时弹系统通知，按条目去重，点击直达会话；页面聚焦时只弹卡不发系统通知。
- **再提醒**：一条「等我」超过 N 分钟（默认 30）没处理，再提醒一次，之后不再重复；可「延后」到指定时间，延后期间同一会话有新的「需要回复」回合时提前回来（参照 Multica 延后提前唤醒）。
- **非 Claude 会话的标记通道**（gofer-iuiq）一并做，否则 suga 类会话永远不进「等我」。

## 6. B 流程推进（二期）

### 6.1 流程模板

内置两套（Q2），按规模选：

| 模板 | 步骤 | 门禁（服务端判定，不读模型正文） |
|---|---|---|
| `feature`（中、大功能） | design → review → plan → doing → verify → done | design 完成：设计稿路径存在且已提交，文档头写 issue id；review 完成：人在「等我」批准，或评审 job 通过（按评审轮次上限）；plan 完成：绑定的 gofer plan 存在且至少一条 todo，计划文档已提交；doing 完成：plan 的 todo 全部 done；verify 完成：验证工作流在包含改动的提交上通过 |
| `small`（小修复） | doing → verify → done | 同上后两步 |

模板可在工作区覆盖（步骤、门禁开关、哪一步需要人），但不支持任意 DAG——那是 workflow 引擎的事。

### 6.2 运行

- **载体**：流程挂在一个工作项上（显式工作项，已有）；工作项绑定常驻会话、issue、设计稿、plan。
- **开始**：会话开工前执行 `gofer flow start <issue> --size feature|small`；SessionStart 注入告诉 agent「实现类工作先开流程」。不做正文启发式判断「这是不是实现」（RV1 / RV2 的经验）。会话没开流程就建 plan / 派实施 job 时，gofer 在命令输出里提示一次（不拦截）。
- **每轮提醒**：终端会话在 UserPromptSubmit 的附加上下文、ACP 会话在每轮输入尾部，注入一小段「流程：当前 plan（下一步 doing）；完成本步执行 `gofer flow done`，要改执行 `gofer flow back`，卡住执行 `gofer flow blocked --reason`」（参照 Multica 每轮注入，放在用户消息尾部不破坏缓存）。
- **推进**：只有显式动作推进（agent 的 `gofer flow done` 或人的批准），gofer 校验门禁后进入下一步；门禁不过返回缺什么。一轮结束本身不推进。
- **放权等级**（Q3，与 plan 推进引擎同一套）：记录（只记它本来会做什么）→ 提醒（下一步该 agent 做时自动给会话送一轮「继续下一步」）→ 自动（同时自动派验证等确定性动作）。需要人的步骤（review 批准、verify 失败）进「等我」。合并到 main、push、发版永远要人。
- **与 plan 推进引擎**：flow 管 plan 之前与之后的阶段；doing 阶段内部 todo 的推进仍由 plan 推进引擎负责。

## 7. D Team（三期）

- **形态**（Q4）：一个团队 = 一个 leader 常驻会话 + 若干成员常驻会话 + 团队说明（只给 leader）。工作区级团队的 leader 就是 gofer-9dbh 的「工作区代理」。人也可以是成员（接收「等我」）。
- **不做**：多 agent 自由群聊、每轮用模型决定谁发言（LoopForge 已撤掉、LobeHub 旧方案的教训）。
- **路由默认值**（确定性，参照 Multica / LobeHub Channel）：成员结果信默认回 leader；人发的消息只到被点名者；leader 的信不唤醒自己；agent 回复可以点名触发，但限跳数（参照 LobeHub 最多 3 跳）、中继带幂等键与来源标注；无点名时只让一个成员先答，其余等它答完再补；已有待跑轮次就合并；每次路由判定落库可查。
- **leader 协议**：每次唤醒注入「协议 + 花名册（名字、用途、状态、当前流程步骤）+ 团队说明」；每轮必须记一条评估（派了活 / 无事 / 失败 + 理由），无事不发言；leader 只派活与汇总，不实现，不把工作项推到 done（留给人）。
- **团队视图**：web 上一个团队页 = 公开层时间线（成员间信件、流程事件、等我）+ 成员列表（五档状态、当前任务）；点一条结果跳到产出它的成员会话。每个成员保留自己的私有会话上下文。
- 依赖：A（成员都是常驻会话）、B（花名册显示流程步骤、leader 按流程派活）、信箱至少一次投递与合并。

## 8. 分期

| 期 | 内容 | 依赖 | 规模 |
|---|---|---|---|
| 一 | A 名册（实体、bind / open、charter 注入、web 名册与弹卡）+ C（「等我」含 ACP 与 suga、推送进门即发且只发一次、服务端再提醒、浏览器通知单一出口）；计划拆 1a / 1b | 无 | 中到大 |
| 一·补 | 固定会话定时（`schedule` 在同一会话发固定话术） | 一 | 小到中 |
| 二 | B 流程（模板、`gofer flow`、门禁、每轮注入、放权等级先只记录 + 提醒） | 一 | 中到大 |
| 三 | D Team | 一、二 | 大 |

每期先核实：Claude ACP 适配器能否加载终端会话（影响 §4.3）；codex 等其他终端 agent 的等价物。已核实（用户 2026-11-19）：Claude Code `--resume` 后会话 id 保持不变，§4.2 的自动续绑按会话 id 即可。

## 9. 决策点（2026-11-19 用户定：全部按推荐）

- **Q1 终端会话迁到 web 的方式**：推荐**两条路并存**——主跟进项目的 2–3 个开发会话留在终端（web 名册可见、可回复、可弹卡），固定用途会话（周报、PR 审查、周分析、部署）改为托管 ACP 会话，web 原生。备选：全部迁成 ACP（终端体验丢失）；全部留终端（固定用途会话仍占终端窗口）。
- **Q2 流程模板**：推荐内置 `feature` / `small` 两套，按 idevstd 的 design → review → plan → doing 加 verify；工作区可覆盖步骤与哪步需要人。备选：完全自定义 YAML（灵活但每个工作区要配）。
- **Q3 自动推进放权**：推荐先上线「记录 + 提醒」两档，像 plan 推进引擎一样量化一致率后再开「自动」。备选：一上来就自动送「继续下一步」。
- **Q4 Team 形态**：推荐 leader + 成员 + 信箱 + 确定性路由，leader 不实现、done 留人；不做自由群聊。
- **Q5 分期顺序**：推荐一期 A + C（直接解决「难找难续」「需要我时没人找」），二期 B，三期 D。备选：先做 B（流程提醒），名册后做。
- **Q6 名称**：新实体还是复用「工作项」概念扩展。定为新实体，名为 `seat`（中文仍叫「常驻会话」）：工作项是「一件事」，常驻会话是「一个长期的人手」，一个常驻会话会先后跟进多个工作项。原推荐名 `resident` 与代码里已有的 resident（ACP 持续会话 job）冲突，2026-11-19 改为 `seat`。
