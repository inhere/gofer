## 背景与目标

现在一批工作的推进是「人 + 监督会话」手工完成的：定方向、写计划、派 job、等通知、审 diff、返工、合并、验证、发版。其中大部分是机械的状态推进，少部分需要判断。gofer 已有不少带 agent 的构件（管家、leader、交付核验、记忆综合），但各自为政、输出多为自由文本、没有接进主流程，实际很少被用。

目标：gofer 能**自己推进一个 plan 到结束**，只在需要人的地方停下来、给出带推荐项的选择；判断交给 agent，但 agent 只能「提出」白名单内的动作，执行、放权、预算、审计都由 gofer 确定性地把关。以后 xhen 接手时，只替换决策点背后的 agent，契约不变。

成功标准（试点用 gofer 自身批次）：只记录模式下，推进引擎在各节点的「本来会做的动作」与人的实际处理一致率达到约定阈值后，逐级放权；放权后人的手工操作次数明显下降（以审计记录统计）。

## 范围与非目标

- 范围：推进引擎、决策点契约、放权等级、统一预算、agent 自报终态、决策卡、实施审查返工的流程模板、job 诊断、批后复盘；现有 leader / 交付核验 / 一次性 agent 调用的收编。
- 非目标：平台内置模型路由；为无人值守放宽权限；外部线程接入（PR / IM，gofer-eeod 的来源部分）放到本设计的最后阶段另行细化；xhen 契约（只保证决策点可替换）。
- 红线（不随放权等级改变）：合并到 main、push、发版、删除数据、改配置与权限，永远出决策卡要人。

## 已确认事实（代码，main 30d92c6b，详见调研记录）

- plan 推进只在写入路径与 job 终态钩子里触发（`job/plandispatch.go`、`job/planadvance.go:161`），**没有后台扫描，重启后不补推进**；根项要 `plan run` 启动；失败把 plan 置 blocked（`maybeBlockPlan` :231）。
- leader：成员终态后经持久化 wake 表一次性起 job（`job/leader.go`），prompt 是自由文本，**没有结构化输出**，靠 6 个 MCP 工具产生副作用；轮数上限 6。
- 管家：常驻 ACP 会话整理工作项，**唯一有「只记录不执行」（observe）模式**的构件（`steward/observe.go`）。
- 交付核验：一次性无工具 job，输入 `job-check/v1` JSON、输出 verdict JSON（`job/delivery_check.go`、`check_types.go`），是**唯一会改变 job 结局的结构化 agent 输出**；fail 时有限次续接，否则转 needs_review；每日限额按进程内存计数。
- 一次性 agent 调用有三套实现（交付核验 `serviceChecker`、记忆综合 `JobOneShot`、会话摘要 bgagent），护栏不一；`bgagent.KindJobCheck` 已声明无人用。
- 自动续接计数器分散：交付核验续接、自动续跑、retry、todo 接续链、leader 轮数各自独立，**没有每 plan 统一预算**。
- 失败处理（`fallback.go`、`execute.go:1170`、`stall.go`）全是确定性规则，可直接作为推进引擎的规则层。
- 可复用：决策钩子（只能拒绝或更保守，`job/decision_hooks.go`）、hold、needs_review、工具审批、调用方上限、三档 job 凭据（member / leader / steward）、第 3 批的审计表与「需要你处理」类。

## 总体方案

### 1. 推进引擎（plan driver）

- **持久化的推进状态**：每个启用推进的 plan 有一行 driver 状态（放权等级、预算余量、当前等待的决策、最近一次推进时间）。事件（job 终态、待验收、交付核验结论、决策回来、定时）写入推进队列表；serve 启动时与每 N 秒扫描一次，**重启后补推进**（修复现状缺口）。现有 `advancePlan` / `maybeBlockPlan` / `linkTodoOutcome` 的分散调用收拢为「投递推进事件」一个入口。
- **规则层（确定性，先于决策点）**：
  - todo 就绪且有执行方 → 派发；
  - job 成功且（无核验 / 核验通过 / 自报 pass）→ 按 complete_on 标完成，推进后继；
  - 偶发失败 → 交现有续跑 / fallback / retry 规则；
  - 预算用尽、红线动作、规则无法判断 → 出决策点或决策卡。
- **放权等级**（每 plan，可按项目设默认）：`record`（只记录「本来会做的动作」，不执行；把管家 observe 推广到推进引擎）/ `assist`（低风险动作自动、其余出决策卡）/ `auto`（预算内自动，红线仍出卡）。
- **动作白名单与风险等级**（固定在代码里，不可配置成更宽）：
  - 低：派发就绪 todo、按决策要点续接（返工）、给 todo 加备注、创建只读诊断 job；
  - 中：跳过 todo、在集成分支合并 worktree、调整 todo 执行方 / 模型、重排后继；
  - 红线（永远出卡）：合并到 main、push、发版、删除、改配置 / 权限 / 放权等级本身。
- **统一预算**（每 plan）：最多 job 数、最多返工轮数（含核验续接、决策返工）、最多决策点调用数、成本与时长上限；现有分散计数器保留各自语义，但同时扣减 plan 预算，用尽即暂停并出卡。

### 2. 决策点（decision point）

- **契约**：`decision/v1` 请求 = {类型、plan / todo / job 摘要、相关事实（报告尾部、diff 统计、核验结论、诊断、历史决策）、可选动作清单（已按放权等级与风险过滤）、预算余量}；响应 = {选择的动作（必须在清单内）、参数、理由、置信度、给人的一句话说明}。schema 校验不过、动作不在清单内、超时 → 一律视为「上交给人」。
- **类型**（有限，逐步加）：`after_failure`（重试 / 带要点返工 / 换执行方 / 跳过 / 上交）、`review`（通过 / 返工 + 要点 / 上交）、`stuck`（无进展时：诊断 / 返工 / 上交）、`next`（plan 内后续安排：派哪个、调整依赖）。
- **执行者**：统一的一次性 agent 调用器（收编三套实现）：一次性 suga job，只读、受限 MCP（只有读取 plan / job / diff 与提交决定），走 bgagent 的硬停止（每日次数 / 成本 / token / 超时）并持久化计数。默认 agent 可配置；以后接 xhen 只换执行者。
- **审计**：每次决策记录请求摘要、响应、gofer 的校验结果与最终执行，写入决策表与审计表。

### 3. agent 自报终态（gofer-jaoy，LoopForge L1 思路）

- job 内 MCP 工具 `gofer_submit_result {decision: pass|rework|fail|human, reason, action_required?, findings?}`，每个 job 每个 attempt 只接受一次。
- 推进引擎把它当作首要信号：human → 出决策卡（带 action_required）；fail 即使 exit 0 也按失败处理；rework 进入返工路径（受预算）。
- 缺失终态：job 正常结束而没提交时，续同一会话一次、只要求提交结论；仍没有则按退出码与核验结论走规则层。
- 任务书模板与 prime 注入加一行说明（按 G046 写成通用文案）。

### 4. 决策卡

- 「等我」的「需要你处理」类新增 `driver.decision` 卡：一句话说明 + 选项（含推荐项与理由）+ 「交给它决定」（把此类决定下放到当前等级上限）；选择后推进引擎继续。卡片动作带 plan 版本与轮次，状态已变则拒绝（gofer-ds7i）。
- 每日一页「推进记录」：做了什么、为什么、花了多少、在等什么（数据来自决策表与审计表）。

### 5. 实施审查返工模板（gofer-5hdh 思路）

- plan 可选一个「交付流程」：`实施 → 审查 → （返工 ≤ N）→ 关卡`。审查是一个 `review` 决策点，资料包含 diff 统计（删除行）、测试结果、越界文件、核验结论与项目的审查清单（项目 rule 记忆里的条目）。
- 返工把审查要点作为续接 prompt；超过轮数上交。关卡（合并 / 发版）按红线出卡。
- 交付核验（现有）作为审查前的确定性门槛之一保留。

### 6. job 诊断（gofer-n3kw）

`gofer job diagnose <id>`：统一终止原因枚举、续跑链首错、阶段时间线（启动、首个输出、最后输出、结束）、确定性分析（证据 / 未知 / 下一步）。作为 `after_failure` / `stuck` 决策点资料包的一部分。

### 7. 批后复盘（gofer-zoww）

plan 结束后确定性统计事实（各 todo 耗时、返工轮数、决策点上交率与理由、同类审查问题、工具重复调用），派一次 `retrospective` 决策点给出白名单内的改进建议（改交付流程参数、加审查清单条目、加项目 rule），人挑选后应用。

### 8. 收编现有构件

- leader 回合：改为 `next` 决策点的一种触发方式（成员终态后），输出结构化；现有 leader MCP 副作用路径在迁移完成后按 G032 删除。
- 交付核验：保留语义，执行改走统一调用器（落实 `KindJobCheck`），每日限额持久化。
- 管家：继续负责工作项整理；其 observe 机制抽成推进引擎与管家共用的「只记录」层。

## 架构

- `internal/job/driver`（新子包，G024 双接口依赖倒置：job 经 `DriverNotifier` 投递事件，driver 经 `JobOps` 取宿主能力）：推进状态、规则层、放权与风险、预算、事件队列。
- `internal/job/decision`（或并入 driver）：契约类型、校验、统一一次性调用器（基于 bgagent Guard）。
- `jobstore`：driver 状态、推进队列、决策表（G057）。
- `serve`：启动扫描与周期扫描；`httpapi` / `mcpserver`：卡片动作、`gofer_submit_result`、只读决策 MCP；`commands`：`gofer plan drive on|off|status --level`、`gofer plan decisions`、`gofer job diagnose`。

## 安全、数据、运维与回滚

- 决策点 agent 只读，凭据只能读取与提交决定；执行一律由 gofer 以 plan owner 的上限进行（调用方上限照常）。
- 红线写死在代码；放权等级的提高本身是红线动作（要人）。
- 预算用尽、决策异常、校验失败一律暂停并出卡，不默认继续。
- 新表加法迁移；推进引擎按 plan 开关，关闭即回到现状行为；回退版本时先关闭推进。

## 验收（总设计层面，阶段计划细化）

- P1：自报终态各分支、缺终态补交一次、诊断输出、统一调用器的硬停止与持久化计数、重启后补推进。
- P2：规则层各分支、record 模式只记录不执行、预算扣减与用尽暂停、对比报告；用 gofer 自身一批作为试点数据。
- 每阶段反向验证：去掉红线检查 → 红线用例失败；去掉预算扣减 → 用尽用例失败；去掉 record 闸门 → 「只记录」用例失败。

## 结论与人工计划 Gate

gofer 加一个确定性的 plan 推进引擎，判断只在四类窄决策点交给一次性 agent，agent 只能从白名单里选动作；放权分三级、红线永远要人、预算统一熔断；先只记录、量化一致率，再逐级放权。第 4 批建议只做 P1 + P2。用户 2026-11-16 批准，Q1–Q6 均取 A；下一步写 P1 + P2 的计划。
